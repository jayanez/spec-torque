# Acceptance and reproducibility

`npm run check` exercises contracts, bilingual rules, unknown evidence, feature scoping, hash preservation, path/symlink rejection, HTTP sessions, bounded provider errors and build compatibility. `npm run package:integrations` creates host runtime assets. These checks do not replace native-client or human acceptance.

## December 1 operational acceptance

On a clean installation, create or import an original EN/ES specification, inspect all practices and source locations, review a clarification/refinement, apply or export it, and reanalyze. Repeat through Claude Code, Codex, OpenCode and Pi with their common-panel path. Confirm no model/GPU/credentials are needed for basic analysis. Exercise incomplete documents, provider/connection failures, source changes after proposal creation, and preservation of existing decisions. Repeat essentials on macOS, Linux and Windows within the hosts' supported surfaces.

## December 4 integrated acceptance

Inside each real client, select a finding, inspect the correct evidence, produce a proposal, review its difference, reject once, accept once, and verify the shared engine's updated revision. Record host version, operating system, installed artifact, steps, results and limitations. SDK types or mocked render tests alone do not pass this acceptance.

## Pilot and corpus

Use original examples and licensed public material with reproducible revisions. At least two reviewers should label ambiguous cases before quality claims. Report precision/recall per check and language, disagreement and unsupported context. Track time to first analysis, installation failures, false positives, accepted/rejected proposals and usability friction. Do not collect source text or telemetry automatically; participants may voluntarily submit sanitized issue reports.

The [corpus protocol](corpus-labeling.md) defines the blind annotation packet,
disagreement handling and adjudication. The [local evaluator](format-corpus.md)
compares engine revisions with those labels when available and reports the
coverage lost to abstentions.

The stable demonstration must include before/after documents, exact commands, reports, rubric/version identifiers and a statement of unresolved limitations. Badge scores identify a specific revision and must not be described as live certification.
