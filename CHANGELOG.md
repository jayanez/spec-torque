# Changelog

## Unreleased

- Markdown report (#126): no report line ends in spaces or tabs, so a committed report passes a host's whitespace check. Evidence still quotes the source line cut at 300 characters; quoted lines are trimmed only in the report, and the JSON assessment keeps the text as cut. Engine and product versions unchanged (0.1.21, 0.3.0): findings and scores do not move.

- `spec-review` skill (#129): a review sequence for model reviews of a specification set. Run the engine first; then one full review with two independent lenses (adversarial and counterfactual), keeping a finding only when both report it or a fresh-context check cannot refute it; apply the findings in one pass; verify on the difference from the reviewed commit with the `changed` scope, the diff and one yes/no question per unchanged line that cites a changed definition; and review in full again only when a fix changes a decision rule, a threshold, the open decisions or the task order. The score is never an acceptance signal. The sequence is a recommendation without a controlled evaluation behind it. Mirrored in the Spanish guide; no new skill, so host packaging is unchanged.

- Codex Desktop (#117): invoke `$spec-setup` to bind a trusted worktree without a terminal step. Choose it from the `$` menu, confirm the root, and approve the protected MCP write. Then open a new local chat for `$spec-view`. Setup also checks and repairs obsolete paths after an update. The workbench environment action remains a separate opt-in.

- Codex Desktop (#116): open the local workbench from the **Project** command palette without a model turn, or use the optional `$spec-workbench` skill. Worktree setup prints the environment action without editing files. [Desktop observations](docs/codex-desktop-probe.md#workbench-launch-in-codex-desktop-2026-11-28-issue-116)

- Engine 0.1.21 (#52, H52c-a), product version unchanged (0.3.0): a scenario step that carries a normative modal (`- THEN the system SHALL lock the account`, `- ENTONCES el sistema DEBE …`, or a sentence that starts with When/Cuando and has a modal) is now a requirement line, as the label guide defines it. It counts for normative wording (E1.4), measurability (E1.2), single obligations (E2.1), identifiers (I1.2, I2.2) and the related findings, exactly like any other requirement line. A step without a modal is still an acceptance step, even with a requirement ID, and fenced or quoted steps are not read. A specification written as scenarios with `SHALL` steps is no longer `unknown` for those practices. The corpus comparison shows no prediction change. See docs/precision-decisions.md.
- Engine 0.1.20 (#52, H52), product version unchanged (0.3.0): a specification heading that carries a requirement ID in the defining position (`### REQ-001 — Keep the export a draft`) now counts as an identified requirement unit for I1.2 (stable unique identifiers) and I2.2 (uniform identifiers), even when only scenario steps or prose without a modal follow it. A specification written only this way is no longer `unknown` for both, and one that also has a requirement line without an ID elsewhere is `partial` instead of `missing`. The heading is cited as evidence. Nothing else changes: the heading is not a requirement line, so the normative-wording, measurability, single-obligation, actor and per-line identifier checks, duplicates and references are as before, and scenario steps and success criteria without a modal still do not count as requirements. Only a heading whose first ID is `FR-`, `NFR-` or `REQ-`, that carries no other ID or removal word (`removed`, `deprecated`, `eliminado`…) and has content under it counts; IDs later in a heading title, dotted sub-IDs, `R-` headings (risks, releases), other ID families (`US-001`, `SPEC-028`), plans and Spec Kit checklists do not. The corpus comparison shows no prediction change. See docs/precision-decisions.md.
- Codex (#115): a `$spec-view [feature | changed [base]]` skill opens the inline viewer through `open_spectorque`, since Codex plugins cannot register slash commands. It ships only in the Codex package (the `prepare:codex` control keeps the shared skills), takes one model turn and is explicit-invocation only. The docs and the connect panel say `$spec-view`. Product version unchanged (0.3.0). Checked by hand in Codex Desktop on macOS: the viewer opens for a feature and for `changed <base>` ([probe notes](docs/codex-desktop-probe.md)).
- Engine 0.1.19 (#92, H92a), product version unchanged (0.3.0): the templates that Spec Kit and Spec Kitty install or ship are no longer discovered. A Markdown file in an installed template folder is not a candidate: `.specify/templates/`, `.specify/presets/<name>/templates/` and `.specify/extensions/<name>/templates/` (Spec Kit, with their subfolders such as `overrides/` and `commands/`), and `.kittify/templates/` and `.kittify/[overrides/]missions/<mission>/templates/` or `command-templates/` (Spec Kitty), at any depth of the repository. It is not listed, read or scored by any host: the CLI, MCP `discover_specs` and `analyze_specs`, the workbench `serve` feature list and workspace reads, VS Code, the other host adapters, GitHub import and the workbench folder import. Their placeholder text (`[FEATURE NAME]`, sample `[NEEDS CLARIFICATION]` markers, example requirements) no longer adds findings, open decisions or requirement IDs to "All documents" and folder scopes, and template folders no longer appear as features. A `templates` folder anywhere else is project content and stays, including one inside a feature kept under `.specify/specs/` or `.kittify/specs/`; it is now sorted by name with the other generic groups instead of last. A single file or caller-supplied artifact text is still analyzed as given; a `--path`, `--feature`, focus or GitHub tree URL that names a template folder fails with "… is a template folder. Spec Kit and Spec Kitty templates are not analyzed." instead of returning an empty set. Feature results do not change. A folder or "All documents" scope whose only specifications were templates now has none, so the checks that need a specification (such as undefined references) report `unknown` instead of findings. The corpus comparison shows no prediction change. See docs/precision-decisions.md.
- Engine 0.1.18 (#104, H104a): P2.1 (functional and user requirement coverage) and C1.1 (behavioral product specification) accept an actor named by role. A spec line that is neither a requirement nor a heading counts when it is a user story (`As a maintainer, I want …`) or when a human role noun (developer, operator, maintainer, reviewer, administrator, owner, engineer, author, contributor, approver, auditor, analyst and their Spanish forms) is the subject of a clause with a present verb (`Given the developer requests …`, `Cuando el operador aprueba …`). A role acting on the specification's own process does not count: lines under clarification, decision, status, risk, assumption, notes, history, review or approval headings, dated lines, past forms and roles acting on the spec, plan or tasks. The existing actor words (`user`, `customer`, `usuario`, …) now count only as whole words and never inside a fenced code block, so "refactor" or "superuser" no longer make these practices `partial`. Both practices move together; nothing else changes, and the corpus comparison shows no prediction change. See docs/precision-decisions.md.
- Engine 0.1.17 (#106, H106), product version unchanged (0.3.0): P1.3 (requirement-level dependency traceability) also accepts a labeled dependency field on a plan or tasks line, `Dependencies:`, `Depends on:`, `Blocked by:`, `Dependencias:`, `Depende de:` or `Bloqueado por:` (optionally bold), when a task or requirement ID follows before the sentence ends: `Dependencies: T001`, `Dependencias: T001, T003`, `Dependencies: T001–T004`. `Dependencies: none`, a dash, an empty value, an ID-less value and prose that only mentions dependencies still do not count. P1.3 only gains evidence and stays `partial` at most; no other practice, finding or open decision changes, and the corpus comparison shows no prediction change. See docs/precision-decisions.md.
- 0.3.0 is published: npm (five packages), the VS Code Marketplace (pre-release), the MCP Registry and a GitHub pre-release. The npm `next` badge is back in the README, with link badges for the VS Code Marketplace (shields.io retired its version badge) and the MCP Registry; Open VSX follows once the `jayanez` namespace is approved.
- The README and Spanish guide open with a one-command start: `npx -y spectorque serve --root .` for the workbench, and `claude mcp add` / `codex mcp add` lines for the MCP server, checked against Claude Code 2.1.311 and Codex CLI 0.170.0 in isolated profiles.
- npm publishing now goes through trusted publishers on all five packages; the first-publish token is removed. The publishing checklist records the npm validation window and the *Allow npm publish* setting, and the public-registry installs are recorded in [compatibility](docs/compatibility.md).

### Internal versions 0.2.1–0.2.9

These versions were bumped on `develop` but not tagged or published. Their changes ship in 0.3.0.

- Engine 0.1.16 (#84, H9), version 0.2.9: a plan or tasks reference that its own line qualifies by another specification no longer produces an I2.3 "has no definition" error. That covers an ID directly qualified by `SPEC-<n>` (`SPEC-028 REQ-004`, `SPEC-028/REQ-004`, `spec-005's FR-023`) or by a hyphen-joined namespace that no spec line of the feature uses (`VPC-REQ-01`). A marker such as "not adopted" does not leave a reference out (that rule was measured and reverted); to cite a proposal that was not adopted, drop the bare ID or prefix it (`PROPOSAL-REQ-007`). A qualifier that is the feature's own (`SPEC-028` in `specs/028-…`, or a namespace its specs use) and a hyphenated range (`FR-001-FR-003`) still resolve locally. Traceability edges are unchanged. The workspace index is not consulted. The corpus comparison shows no prediction change. See docs/precision-decisions.md.
- Engine 0.1.15 (#79, H7a), version 0.2.8: a Markdown file under a Spec Kit feature's `checklists/` folder is a review context document, whatever its basename. Its lines are never read as requirements text or as open decisions, so a checklist that cites `REQ-001` no longer creates a duplicate identifier, its items no longer lack an identifier or count toward spec-only practices, and `No [NEEDS CLARIFICATION] markers remain` is no longer an open decision. Practices that read context documents (E1.1, P2.5 and others) still count its lines. Known limits are in [precision decisions](docs/precision-decisions.md).
- Engine 0.1.14 (#85, H85), version 0.2.7: E1.3 no longer reports "The subject depends on a pronoun" when `this` or `that` leads a noun phrase ("This amendment MUST …"). It still reports `it`, `esto`, `eso`, `ello`, and `this`/`that` before punctuation, a contraction, a modal or auxiliary, an adverb, a preposition or a verb form. E1.3 findings are only removed; statuses, scores and other findings do not change, and the corpus comparison shows no prediction change. E1.2 detection is unchanged. The clarifier answers "names an option" for a quoted or code-formatted label after a label noun (class, category, label, tag, status, state, type, tier and their Spanish equivalents), including multi-word labels such as `` the class `easily copied` ``.
